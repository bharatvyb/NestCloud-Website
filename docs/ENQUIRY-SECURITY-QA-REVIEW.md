## 2. Security and functional evidence

| Area | Verified in source / local tests | Limits of that evidence |
|---|---|---|
| Required fields and consent | `Code.gs:53–94` rejects unknown/duplicate parameters, controls, bad types, invalid Indian mobile/PIN, unsupported categories and irrelevant fields. Consent is literal `yes`; new submissions must match the server consent version (`Code.gs:111`). | Consent is a recorded assertion, not identity, email or phone verification. Owner approval of consent/retention and live Script Properties are not verified. |
| Price integrity | Fixed server allowlist; integer displayed price is only compared, never trusted as the stored price. A mismatch writes no row and produces an explicit price-review result (`Code.gs:112`). Accepted exact retries recover their original receipt before current catalogue/consent changes. | A stale frontend catalogue requires an updated website/reload and customer review; do not silently rewrite an agreed price. Live catalogue/deployment versions must be aligned manually. |
| Exact native contract | Actual FormData includes one UUID v4, purpose, consent version, checkbox `yes`, empty honeypot and relevant type-specific fields. Purchase has `configuration_id`, numeric INR `displayed_price`, PIN; support references are absent from purchase/general. Native UTF-8 URL-encoding and CRLF length are checked. Exactly 20,000 encoded bytes is accepted locally; 20,001 is blocked. | Browser navigation is stubbed in component tests. Google's decoding/event object was not observed live. No cross-origin fetch, JSONP or opaque success assumption exists. |
| Sheet tab and writing | Actual processor selects Purchase Enquiries / General Contact / Technical Support and server prices/capacities. Adapter checks all schemas, formats cells as text, escapes formula prefixes and stores reference/PIN/phone strings (`Code.gs:127`, `140`, `158`). | These tests use fake Sheets APIs. Real formatting, permissions, leading zeros, formula non-execution and durable row storage are unverified. |
| Duplicate/concurrent submissions | Lock covers metadata read, duplicate/rate checks, append and flush. UUID + normalized payload hash recovers one receipt; same ID with changed details conflicts. A new ID is a different enquiry, subject to limits. Overlapping lock simulation prevents a second write. | Not real simultaneous Apps Script executions. Human/external writers, row deletion/corruption and separate script projects are outside that lock. |
| Ambiguous writes / success | Append/flush faults return “could not confirm,” not success. Persist-then-error followed by unchanged React retry recovers the row's receipt locally. Success is generated only after append/flush or an existing matching record (`Code.gs:129`). | Sheets is not an ACID database. Real partial writes, outages and Google response failures need live verification. |
| Rate/abuse controls | Accepted-row cooldown, global window and capacity cap run under the lock; accepted duplicates bypass new-submission limits (`Code.gs:116`). Honeypot and field/body bounds are enforced. | **Basic abuse controls only.** Anonymous callers can rotate emails, bypass a honeypot or consume execution quota without accepted rows. No trusted IP/origin authentication exists. Do not promise strong bot protection or high availability. |
| Public access and safe rendering | `doGet` never reads Sheets or returns submissions. Helpers are private `_` names. Receipt/message/price/URL slots are escaped before force-printing. Return origins are allowlisted; no arbitrary redirect or personal details in result pages (`Code.gs:11`, `32`, `164`). | Google execution/sharing settings, Script Properties, owners/editors and actual Sheet ACLs cannot be inferred from source. Public endpoint must execute as the owner; the Sheet itself must remain restricted. |
| Personal data / telemetry | No enquiry fields are added to website URLs, analytics or app logs. Only the public configuration ID is in selection URLs. Submitted raw fields and retry fingerprint are stored in tab-local sessionStorage with explicit clear/expiry. | Same-origin scripts/XSS can read those drafts. Browser suspension/session restoration can delay physical storage deletion; 24 hours is not a background erasure guarantee while code is not running. Google platform metadata/logging is outside this repository. |

No credentials, live endpoint, Sheet ID, real customer details or live deployment secret were added. Backend source and its restrictive manifest are unchanged from PR #3.

## 3. Customer journey and browser behavior

- Purchase: select storage → review correct product price → Enquire to Buy → matching native form; no device serial or payment fields. Existing URL/session/history selection tests pass.
- General: Contact Us → required message; no PIN/configuration/device fields.
- Support: Technical Support → required problem description and optional order/serial/topic. An unrelated configuration query does not change purpose.
- Submissions save the exact draft before native navigation. Successful or failed result-page Back is handled with `pageshow`; unchanged normalized payload reuses the ID. Intentional changed details/configuration produce a new ID at the next valid submit. Invalid attempts preserve input and do not replace the previously submitted snapshot. Reload restores the submitted snapshot; unsent edits are not autosaved.
- Same email is not a duplicate key. Email case, mobile spacing and outer whitespace are normalized in line with the server. Clearing removes the saved snapshot, unchecks consent and generates a new ID; expired/corrupt drafts cannot restore personal details.
- The confirmation URL is a normal POST navigation. There is no POST/Redirect/GET implementation or HTTP redirect API used here. Refresh/Back/Forward may show a browser resubmission warning or Google wrapper behavior; do not claim those prompts are eliminated. Unchanged same-ID repeats are safe in processor tests, not proven through Google's live wrapper. A customer who already received confirmation is told not to resend.
- Google's result HTML has a user-activated `_top` return link, consistent with its sandbox restrictions. Owner must set `RETURN_URL` to the actual website host. If testing on GitHub Pages with the default `nestcloud.in` return URL, the new homepage recovery UI will not be reached. That setting is a release prerequisite.
- First-time customers see required/optional labels, a clear consent notice, no payment collection and a visible fallback before typing when disabled. The temporary live reservation form has older models and does not receive the selected configuration or price. Its delivery and submission remain unverified; it cannot be counted as proof that the native journey works.

Official platform references: [Apps Script POST event/deployment](https://developers.google.com/apps-script/guides/web), [Google HTML sandbox/navigation](https://developers.google.com/apps-script/guides/html/restrictions), [GitHub PR target-branch filters](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request). These describe platform behavior, not tests of this deployment.

## 5. Production gates and unverified real-world behavior

**NO-GO to enable the native service or replace the live site's enquiry path today.** Before launch, the owner must:

1. Deploy/authorize the reviewed Apps Script against a private test Sheet; verify anonymous access and owner execution without exposing the Sheet or credentials. Confirm actual Script Properties, sharing/editors and the three exact schemas.
2. Set the public endpoint and approved consent version for the website build, match server `CONSENT_VERSION`, set the correct allowlisted `RETURN_URL`, and explicitly authorize a later publication. No such settings/deployment were performed in this audit.
3. Exercise all three native POSTs in real browsers, observe the intended private tab rows and matching receipt, then verify Google-hosted success/error/price pages and return recovery. A mock receipt is not a real enquiry receipt.
4. Verify duplicate same-ID retry, invalid fields, mismatched prices/consent, simultaneous requests, rate/capacity limits and an ambiguous write failure in a controlled Google test environment. Check text formatting/formula defense in the actual Sheet.
5. Test Chrome/Safari/Firefox as applicable on desktop/mobile, including Google wrapper warnings, POST refresh/resubmission prompts, Back/Forward cache, tab reuse, reload, expiry and blocked/full storage. Quota/outage and retention/deletion procedures remain operational limits.
6. Approve consent/retention handling and modest-volume abuse/availability limits. The service has neither CAPTCHA nor authenticated callers, and does not promise strong bot protection.

Lint is an explicit remaining tooling gap. Live persistence, actual Google confirmation rendering, project/Sheet permissions, real concurrency, quota behavior and external fallback submission are all unverified. Nothing was merged, published or deployed, and DNS was not changed.
